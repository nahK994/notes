এই পুরো document-টা দাও, আমি diagram-সহ সুন্দর করে পুরোটা দিয়ে দিই। তাহলে তুমি সরাসরি copy করে বসিয়ে দিতে পারবে।

## Pipe: দুটো Process-এর মধ্যে কথোপকথন

Unix-এর সবচেয়ে শক্তিশালী idea কোনটা জিজ্ঞেস করলে অনেক পুরনো programmer একটাই উত্তর দেবে।

**Pipe।**

একটা ছোট্ট `|` চিহ্ন। কিন্তু এই চিহ্নটা Unix-এর পুরো দর্শনকে ধারণ করে। ছোট ছোট program বানাও, প্রতিটা একটাই কাজ করুক, তারপর এদের জুড়ে দাও — এটাই Unix way। Pipe হলো সেই জোড়ার আঠা।

---

### Pipe কী?

তুমি কি কখনো দেখেছো রান্নাঘরে গ্যাসের পাইপ কীভাবে কাজ করে? এক প্রান্তে গ্যাস ঢোকে, অন্য প্রান্তে বের হয়। মাঝখানে কোনো জমা হওয়ার জায়গা নেই — যা ঢোকে তা বেরিয়ে যায়।

OS-এর Pipe ঠিক এরকম। এক process যা লেখে, অন্য process তা পড়ে।

```
Process A                              Process B
─────────                              ─────────
stdout (FD 1) ──────[ PIPE ]──────► stdin (FD 0)

A যা লেখে                             B তা পড়ে
```

`ls | grep .go` লিখলে কী হয়?

```
ls-এর output ──────[ PIPE ]──────► grep-এর input

ls:   "main.go"                    grep: "main.go" রাখো
      "README.md"                         "README.md" বাদ
      "utils.go"                          "utils.go" রাখো
      "go.mod"                            "go.mod" বাদ
                                          ↓
                                    screen-এ দেখায়:
                                    main.go
                                    utils.go
```

`ls` জানে না তার output কোথায় যাচ্ছে। `grep` জানে না তার input কোথায় থেকে আসছে। দুজনেই ভাবছে নিজের FD-তে লিখছে বা পড়ছে। Pipe মাঝখানে চুপচাপ কাজ করছে।

---

### Pipe ভেতরে কীভাবে কাজ করে?

Pipe আসলে Kernel-এর memory-তে একটা ছোট্ট **buffer** — সাধারণত ৬৪ KB।

```
┌─────────────────────────────────────────────────────┐
│                  KERNEL MEMORY                      │
│                                                     │
│   ls (writer)        Pipe Buffer        grep        │
│   ──────────         ───────────        ────────    │
│                                                     │
│  write(fd=1) ──►  [data data data]  ──► read(fd=0) │
│                   [             ]                   │
│                   [  64 KB max  ]                   │
│                                                     │
│  ls লেখে ──────────────────────────► grep পড়ে     │
└─────────────────────────────────────────────────────┘
```

এই buffer-এর দুটো মুখ থাকে — একটা লেখার জন্য, একটা পড়ার জন্য:

```go
r, w, _ := os.Pipe()

// r = read end  (FD, যেখান থেকে পড়া যায়)
// w = write end (FD, যেখানে লেখা যায়)
```

`os.Pipe()` দুটো FD দেয়। একটায় লেখো, অন্যটা থেকে পড়ো। মাঝখানে Kernel-এর buffer।

পুরো ছবিটা এরকম — `ls | grep .go` চালালে Kernel-এর ভেতরে আসলে কী হচ্ছে:

```
                        KERNEL
┌──────────────────────────────────────────────────────┐
│                   PIPE BUFFER                        │
│  ┌───────────────────────────────────┐               │
│  │  [main.go\nexecutor.go\n...]      │               │
│  └────────────────┬──────────────────┘               │
│      read(FD 3)   │         │  write(FD 4)           │
└───────────────────┼─────────┼────────────────────────┘
                    │         │
          ┌─────────┘         └──────────┐
          │                              │
          ▼                              ▼
┌──────────────────┐          ┌──────────────────┐
│  grep (child 2)  │          │   ls  (child 1)  │
│                  │          │                  │
│  FD 0 → pipe read│          │ FD 1 → pipe write│
│  FD 1 → screen   │          │ FD 0 → keyboard  │
│                  │          │                  │
│  pipe থেকে পড়ে  │◄─────────│  pipe-এ লেখে    │
│  screen-এ দেখায় │          │                  │
└──────────────────┘          └──────────────────┘

ls জানে না সে pipe-এ লিখছে  — ভাবছে FD 1 = screen
grep জানে না সে pipe থেকে পড়ছে — ভাবছে FD 0 = keyboard
```

---

### dup2 কী? কেন দরকার?

এখানেই আসল জায়গা। একটু মনোযোগ দিয়ে পড়ো।

`ls | grep .go` চালালে Shell দুটো child তৈরি করে। `ls`-child আর `grep`-child।

এখন সমস্যা হলো — জন্মের পর `ls`-child-এর FD 1 screen-এ point করছে। কিন্তু আমরা চাই `ls` যা লেখে সেটা screen-এ না গিয়ে pipe-এ যাক। অর্থাৎ FD 1 কে pipe-এর write end-এ point করাতে হবে।

এই কাজটাই করে **`dup2()`**।

`dup2(oldFD, newFD)` মানে হলো — *"oldFD যেখানে point করছে, newFD-কেও সেখানে point করাও।"*

```
dup2(pipeW, 1) মানে:

আগে:                        পরে:
FD 1 ──► screen             FD 1 ──► pipeW (pipe-এর write end)
pipeW ──► pipe              pipeW ──► pipe

এখন FD 1 আর screen-এ যাচ্ছে না।
FD 1-এ যা লেখা হবে সব pipe-এ যাবে।
```

`ls` নিজে কিছু জানে না। সে শুধু জানে FD 1-এ লিখতে হবে। Shell আড়াল থেকে সেই FD 1-এর destination বদলে দিয়েছে।

---

### dup2 ঠিক কখন হয়?

এটা অনেকের মাথায় গুলিয়ে যায়। তাই একদম পরিষ্কার করে বলি।

**`dup2` হয় `fork()`-এর পরে, `exec()`-এর আগে।**

কেন? কারণ তিনটা ধাপের সময়কাল মনে করো:

```
fork()  → child জন্মালো, এখনো shell-এর copy
            │
            │ ← এই ফাঁকে dup2() করো
            │   FD বদলে দাও
            │   এখানে child এখনো আমাদের নিয়ন্ত্রণে
            │
exec()  → child নতুন program হয়ে গেলো
            │
            │ এখন আর কিছু করার নেই
            │ exec() সব memory মুছে নতুন করে দেয়
            │ কিন্তু FD গুলো টিকে থাকে
            ▼
ls চলছে, FD 1-এ লিখছে = pipe-এ যাচ্ছে
```

`exec()` হয়ে গেলে আর FD বদলানোর সুযোগ নেই — নতুন program শুরু হয়ে গেছে। আর `fork()`-এর আগে করলে parent-এর FD বদলে যাবে, সেটাও চাই না।

তাই একমাত্র সঠিক জায়গা হলো `fork()`-এর পরে, `exec()`-এর আগের সেই ছোট্ট ফাঁকটুকু।

---

### Shell কীভাবে Pipe তৈরি করে — পুরো ছবি

এখন পুরোটা একসাথে দেখি। `ls | grep .go` চালালে Shell ধাপে ধাপে কী করে:

**ধাপ ১ — Pipe তৈরি করো:**

```
Shell:
os.Pipe() → দুটো FD পেলো
  pipeR (FD 3) = পড়ার মুখ
  pipeW (FD 4) = লেখার মুখ
```

**ধাপ ২ — `ls`-এর জন্য fork করো:**

```
Shell → fork() → ls-child জন্মালো

ls-child এখন shell-এর হুবহু copy:
  FD 0 → keyboard
  FD 1 → screen    ← এটা বদলাতে হবে
  FD 2 → screen
  FD 3 → pipeR
  FD 4 → pipeW
```

**ধাপ ৩ — exec()-এর আগে ls-child-এর FD 1 বদলাও:**

```
ls-child এখনো চলছে, exec() হয়নি।
এই মুহূর্তে dup2(pipeW, 1) করো:

  FD 0 → keyboard
  FD 1 → pipeW    ← screen থেকে pipe-এ গেলো
  FD 2 → screen
  FD 3 → pipeR    ← এগুলো আর লাগবে না, বন্ধ করো
  FD 4 → pipeW    ← এগুলো আর লাগবে না, বন্ধ করো
```

**ধাপ ৪ — exec() করো:**

```
ls-child → exec("/bin/ls")

ls চলছে এখন। সে শুধু জানে FD 1-এ লিখতে হবে।
FD 1 এখন pipe-এ। ls-এর output pipe-এ যাচ্ছে।
ls নিজে এটা জানে না।
```

**ধাপ ৫ — `grep`-এর জন্য fork করো:**

```
Shell → fork() → grep-child জন্মালো

grep-child এখন shell-এর হুবহু copy:
  FD 0 → keyboard  ← এটা বদলাতে হবে
  FD 1 → screen
  FD 2 → screen
  FD 3 → pipeR
  FD 4 → pipeW
```

**ধাপ ৬ — exec()-এর আগে grep-child-এর FD 0 বদলাও:**

```
grep-child এখনো চলছে, exec() হয়নি।
এই মুহূর্তে dup2(pipeR, 0) করো:

  FD 0 → pipeR    ← keyboard থেকে pipe-এ গেলো
  FD 1 → screen
  FD 2 → screen
  FD 3 → pipeR    ← এগুলো আর লাগবে না, বন্ধ করো
  FD 4 → pipeW    ← এগুলো আর লাগবে না, বন্ধ করো
```

**ধাপ ৭ — exec() করো:**

```
grep-child → exec("grep .go")

grep চলছে এখন। সে শুধু জানে FD 0 থেকে পড়তে হবে।
FD 0 এখন pipe-এ। grep pipe থেকে পড়ছে।
grep নিজে এটা জানে না।
```

পুরো flow একসাথে:

```
Shell
  │
  ├─ os.Pipe() ──────────────────── [pipeR, pipeW] তৈরি
  │
  ├─ fork() ──────────────────────► ls-child
  │                                    │
  │                              dup2(pipeW, 1)
  │                              FD 1 → pipe
  │                                    │
  │                              exec("ls")
  │                              ls লিখছে → pipe-এ যাচ্ছে
  │
  ├─ fork() ──────────────────────► grep-child
  │                                    │
  │                              dup2(pipeR, 0)
  │                              FD 0 → pipe
  │                                    │
  │                              exec("grep .go")
  │                              pipe থেকে পড়ছে → screen-এ দেখাচ্ছে
  │
  └─ wait() ── দুজন শেষ হলে prompt দেখালো
```

### Pipe-এর দুটো গুরুত্বপূর্ণ আচরণ

**Buffer ভরে গেলে `ls` আটকে যায়।**

Pipe-এর buffer মাত্র ৬৪ KB। `ls` যদি অনেক দ্রুত লেখে কিন্তু `grep` ধীরে পড়ে, buffer ভরে যাবে। তখন `ls` আপনাআপনি থেমে যাবে — `grep` একটু পড়ুক, জায়গা হোক, তারপর আবার লিখবে।

এটা error না। এটা **backpressure** — দুটো process নিজে থেকেই synchronized হয়ে যায়, কোনো extra কোড ছাড়াই।

```
ls ──► [████████████ FULL] ◄── grep পড়ছে
              │
        buffer ভরে গেলে ls থামে
        grep পড়লে জায়গা হয়
        ls আবার লেখে
```

**`ls` শেষ হলে `grep` জানতে পারে।**

`ls` exit করলে pipe-এর write end বন্ধ হয়ে যায়। `grep` পড়তে গিয়ে দেখে আর data আসছে না — EOF। সে বুঝে যায় কাজ শেষ, সেও exit করে।

কোনো আলাদা message পাঠাতে হয় না। Pipe বন্ধ হওয়াটাই signal।

### Chain করা যায় যতখুশি

```bash
cat server.log | grep ERROR | sort | uniq -c | sort -rn | head -10
```

```
cat ──► grep ──► sort ──► uniq ──► sort ──► head
         │                  │               │
      ERROR               গোনো          শুধু top 10
      ফিল্টার             duplicate
```

৬টা আলাদা program। প্রত্যেকে একটাই কাজ জানে। Pipe দিয়ে জুড়লে একসাথে একটা শক্তিশালী tool তৈরি হয়।

কেউ কাউকে চেনে না। কেউ জানে না পাশে কে আছে। সবাই শুধু নিজের FD-তে লেখে বা পড়ে।

---

### কেন Pipe এত শক্তিশালী?

কারণ এটা Unix-এর একটা মূল দর্শনকে সত্যি করে তোলে:

> *"একটা program একটাই কাজ করুক, সেটা ভালোভাবে করুক।"*

`grep` শুধু filter করে। `sort` শুধু সাজায়। `wc` শুধু গোনে। এরা কেউ জানে না input কোথায় থেকে আসছে, output কোথায় যাচ্ছে।

কিন্তু Pipe দিয়ে জুড়লে এই ছোট ছোট program গুলো মিলে এমন কাজ করতে পারে যা একা একা করা কঠিন হতো।

ছোট জিনিস জুড়ে বড় জিনিস বানানো — এটাই Pipe-এর আসল শক্তি।
