## File Descriptor: OS-এর সবচেয়ে সুন্দর আইডিয়া

কিছু concept আছে যেগুলো প্রথমে দেখলে অদ্ভুত লাগে, কিন্তু বুঝলে মনে হয় — *এত সুন্দর জিনিস কেউ কীভাবে ভাবলো?*

File Descriptor সেরকমই একটা জিনিস।

Pipe বুঝতে হলে FD জানতে হবে। I/O Redirection বুঝতে হলে FD জানতে হবে। Shell-এর ভেতরের অর্ধেক কাজকর্ম বুঝতে হলে FD জানতে হবে। তাই এটাকে ভালো করে বোঝার সময় নেওয়া দরকার।

---

### FD কী?

Process যখন বাইরের জগতের সাথে কথা বলে — screen-এ লেখে, keyboard পড়ে, file খোলে — সে একটা **ছোট্ট নম্বর** দিয়ে কাজ করে। এই নম্বরটাই **File Descriptor**।

কিন্তু এই নম্বরটা কোথায় থাকে? Kernel-এর কাছে। Kernel প্রতিটা process-এর জন্য একটা table রাখে — কোন নম্বর আসলে কোথায় যাচ্ছে:

```
Kernel-এর FD Table (process 1234-এর জন্য):
┌─────┬──────────────────────────────────────────┐
│ FD  │ আসলে কোথায় যাচ্ছে                         │
├─────┼──────────────────────────────────────────┤
│  0  │ /dev/pts/0  (তোমার terminal keyboard)    │
│  1  │ /dev/pts/0  (তোমার terminal screen)      │
│  2  │ /dev/pts/0  (তোমার terminal screen)      │
│  3  │ /home/user/notes.txt  (তুমি খুলেছো)        │
│  4  │ (খালি)                                    │
└─────┴──────────────────────────────────────────┘
```

তুমি লক্ষ্য করো — FD 0, 1, 2 তিনটাই একই জায়গায় (`/dev/pts/0`) point করছে, কিন্তু তিনটার ভূমিকা আলাদা।

---

### তিনটা FD যেগুলো নিয়ে জন্মায় প্রতিটা Process

Linux-এ প্রতিটা process — সে `ls` হোক, `grep` হোক, বা তোমার নিজের প্রোগ্রাম হোক — জন্মের মুহূর্তেই তিনটা FD পায়। বিনামূল্যে, কোনো কোড না লিখেই।

```
যেকোনো Process (জন্মের পর):
├── FD 0 ──► stdin   ← এখান থেকে input পড়ো
├── FD 1 ──► stdout  ← এখানে normal output লেখো
└── FD 2 ──► stderr  ← এখানে error লেখো
```

**stdin, stdout, stderr** — এই তিনটা নাম তুমি বারবার দেখবে। মনে রাখার সহজ উপায়:

- `stdin` = **in** — বাইরে থেকে আসে (keyboard)
- `stdout` = **out** — বাইরে যায় (screen)
- `stderr` = **err** — error বাইরে যায় (screen, কিন্তু আলাদা channel)

stdout আর stderr দুটোই screen-এ দেখায়, তাহলে আলাদা কেন? কারণ তুমি চাইলে এদের আলাদাভাবে redirect করতে পারো। Normal output file-এ পাঠাও, কিন্তু error screen-এ রাখো — এটা FD আলাদা থাকার কারণেই সম্ভব।

---

### FD নিয়ে সবচেয়ে গুরুত্বপূর্ণ কথা

এখানেই পুরো জিনিসটা সুন্দর হয়ে যায়।

> **FD মাত্র একটা নম্বর। Kernel জানে এই নম্বর কোথায় point করে। তুমি সেই point পরিবর্তন করতে পারো।**

এটাই pipe এবং redirection-এর সম্পূর্ণ রহস্য। আর কিছু না।

```
সাধারণ অবস্থায়:
FD 1 ──────────────────► terminal screen

তুমি FD 1 কে বদলে দিলে:
FD 1 ──────────────────► myfile.txt

এখন program যা-ই FD 1-এ লিখুক,
সেটা screen-এ না গিয়ে file-এ যাবে।

Program জানেও না কী হচ্ছে।
সে শুধু জানে — "FD 1-এ লিখতে হবে।"
বাকিটা Kernel-এর ব্যাপার।
```

`ls > output.txt` লিখলে Shell ঠিক এটাই করে। `ls` প্রোগ্রামকে কিছু বলে না। শুধু তার FD 1 টা চুপচাপ file-এ ঘুরিয়ে দেয়।

---

### একটা উদাহরণ দিয়ে পুরোটা দেখি

`fmt.Println("hello")` লিখলে Go আসলে কী করে?

```
Go কোড:
fmt.Println("hello")
        │
        │  Go runtime এটাকে OS-এর ভাষায় translate করে
        ▼
System Call:
write(fd=1, data="hello\n", length=6)
        │
        │  Kernel FD table দেখে:
        │  "এই process-এর FD 1 মানে terminal screen"
        ▼
Terminal screen-এ "hello" দেখায়
```

এখন যদি program চালানোর আগে FD 1 কে একটা file-এ point করানো হতো?

```
write(fd=1, data="hello\n", length=6)
        │
        │  Kernel FD table দেখে:
        │  "এই process-এর FD 1 মানে output.txt"
        ▼
output.txt ফাইলে "hello" লেখা হয়
```

`fmt.Println`-এর কোড একটা অক্ষরও বদলায়নি। শুধু FD 1 এর destination বদলেছে। এটাই Unix-এর elegance।

### File খুললে নতুন FD তৈরি হয়

```go
f, _ := os.Open("notes.txt")
// f.Fd() = 3  ← Kernel দিলো পরবর্তী খালি নম্বর
```

এখন FD table দেখতে এরকম:

```
FD 0 ──► keyboard
FD 1 ──► screen
FD 2 ──► screen
FD 3 ──► notes.txt  ← নতুন যোগ হলো
```

`f.Close()` করলে FD 3 আবার খালি হয়। Kernel সেই slot টা পরবর্তী কাজের জন্য রেখে দেয়।

একটা ছোট্ট কিন্তু গুরুত্বপূর্ণ নিয়ম — Kernel সবসময় **সবচেয়ে ছোট খালি নম্বর** দেয়। FD 3 বন্ধ থাকলে পরের file খুললে সেটা FD 3 পাবে, FD 5 না। এই নিয়মটা pipe implement করার সময় কাজে আসবে।

### FD-কে ভিজুয়ালি মনে রাখো

```
┌─────────────────────────────────────────────────────┐
│                  একটা Running Process               │
│                                                     │
│   ┌─────┐                                           │
│   │ FD 0│ ◄────────────── keyboard (stdin)          │
│   ├─────┤                                           │
│   │ FD 1│ ──────────────► screen   (stdout)         │
│   ├─────┤                                           │
│   │ FD 2│ ──────────────► screen   (stderr)         │
│   ├─────┤                                           │
│   │ FD 3│ ──────────────► notes.txt                 │
│   ├─────┤                                           │
│   │ FD 4│    (খালি)                                  │
│   └─────┘                                           │
│                                                     │
│   এই table-টা Kernel রাখে। Process শুধু                │
│   নম্বর জানে — পেছনে কী আছে জানে না।                    │
└─────────────────────────────────────────────────────┘
```

---

FD-এর গল্প এখানেই শেষ না। এই ছোট্ট নম্বরটা দিয়েই Pipe কাজ করে — এক process-এর FD 1 আর অন্য process-এর FD 0 কে একসাথে জুড়ে দিলেই Pipe তৈরি হয়।

সেটা পরের অধ্যায়ে।
